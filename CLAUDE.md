# Инструкции проекта

## Главная цель

Разработать семестровый проект в соответствии с требованиями,
зафиксированными в `assignment/SPEC.md`.

Перед началом любой существенной работы прочитай:

- `assignment/SPEC.md`
- `assignment/SOURCE_NOTES.md`
- `assignment/OPEN_QUESTIONS.md`

Для криптографических алгоритмов используй документы из:

`assignment/standards/`

## Приоритет источников

Если источники противоречат друг другу, используй следующий приоритет:

1. Явная информация от пользователя в текущей задаче.
2. `assignment/SPEC.md`.
3. `assignment/SOURCE_NOTES.md`.
4. Приложенные ГОСТы для технических деталей.
5. Собственные предположения.

Не превращай предположение в подтверждённое требование.

При неоднозначности зафиксируй её в `.ai/DECISIONS.md`
или остановись и задай вопрос, если решение существенно влияет на проект.

## Язык

- Общение со мной — на русском.
- Проектная документация — на русском.
- `.ai/*.md` — на русском.
- README — на русском, если явно не указано другое.
- Имена переменных, функций, классов, файлов исходного кода
  и другие программные идентификаторы — на английском.
- Git commit messages — на английском.

## Стиль разработки

- Реализуй только то, что требуется для задания.
- Следуй YAGNI.
- Не добавляй функции "на будущее".
- Предпочитай простое решение сложному.
- Не создавай лишние абстракции.
- Не рефактори несвязанный код.
- Не добавляй новые зависимости без необходимости.

## Комментарии в коде

Не пиши объясняющие комментарии в исходном коде.

Код должен быть понятен через:

- хорошие имена;
- небольшие функции;
- понятную структуру.

Комментарий допустим только тогда, когда без него невозможно понятно
объяснить нетривиальное ограничение или особенность криптографического
алгоритма.

Вместо комментариев веди документацию.

## Рабочая документация

Поддерживай:

- `.ai/PLAN.md` — текущий план;
- `.ai/PROGRESS.md` — выполненные этапы;
- `.ai/DECISIONS.md` — технические решения и их причины;
- `.ai/NOTES.md` — временные рабочие заметки.

`.ai/` является внутренней рабочей документацией и не должна попадать в Git.

Документация, которая является частью сдаваемого проекта,
должна находиться в `docs/` или `README.md`.

## Криптография

Не придумывай реализации криптографических алгоритмов по памяти,
если соответствующий ГОСТ предоставлен в `assignment/standards/`.

Используй предоставленные ГОСТы как первичный источник.

Где в ГОСТе присутствуют контрольные примеры,
создавай автоматизированные тесты по этим примерам.

Успешный round-trip:

encrypt -> decrypt

или:

sign -> verify

сам по себе недостаточен для подтверждения корректности реализации.

## Процесс работы

Для каждого законченного изменения:

1. Прочитай соответствующие требования.
2. Проверь существующий код.
3. Обнови план при необходимости.
4. Реализуй минимальное корректное изменение.
5. Добавь или обнови тесты.
6. Запусти релевантные тесты.
7. Запусти formatter/linter/type checker, если они настроены.
8. Просмотри diff.
9. Обнови `.ai/PROGRESS.md`.
10. Только после успешных проверок сделай commit.

## Git

Используй небольшие атомарные commits.

Один commit должен соответствовать одному логическому изменению.

Перед commit:

- тесты должны проходить;
- diff должен быть просмотрен;
- временные файлы не должны быть staged;
- `.ai/` не должен быть staged;
- секреты не должны попадать в Git.

Не используй force push.

Не переписывай опубликованную историю Git.

Первые этапы проекта не push автоматически.
Создавай commits локально.

Push выполняй только после явного разрешения пользователя.

## Самостоятельность

Не спрашивай разрешения на обычные локальные решения,
если они очевидно следуют из спецификации.

Остановись и задай вопрос, если:

- требование действительно неоднозначно;
- требуется разрушительная операция;
- нужны credentials или секреты;
- существует несколько существенно разных архитектурных решений;
- решение может противоречить требованиям преподавателя.

## Параллельные агенты

Используй subagents только для действительно независимых задач.

Допустимые примеры:

- один агент анализирует ГОСТ, другой изучает существующий код;
- один агент реализует функциональность, второй независимо проводит review.

Не запускай несколько агентов для изменения одних и тех же небольших файлов.
