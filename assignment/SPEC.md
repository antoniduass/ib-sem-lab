# Спецификация семестрового проекта

Версия: 2 (2026-10-14).

## 1. Назначение проекта

Учебное веб-приложение по информационной безопасности, демонстрирующее:

- регистрацию пользователей;
- аутентификацию;
- три уровня доступа;
- трёхфакторную аутентификацию;
- восстановление пароля;
- хэширование паролей;
- симметричное шифрование;
- асимметричное шифрование;
- электронную цифровую подпись;
- хранение и экспорт зашифрованных сообщений.

Главный приоритет — выполнение требований преподавателя
и соответствие приложенным ГОСТам.

## 2. Источники и как читать этот документ

Источники:

- явные указания пользователя в рабочих задачах;
- `assignment/SOURSE_NOTES.md` — заметки с лекции (мои, старосты, фото доски);
- `assignment/OPEN_QUESTIONS.md` — исходный список вопросов;
- `assignment/standarts/` — ГОСТ 34.10-2018, 34.11-2018, 34.12-2018, 34.13-2018.

Каждое требование отнесено к одной из категорий:

| Категория | Префикс | Значение |
|---|---|---|
| Подтверждённое требование преподавателя | `ТП-` | Обязательно. Изменяется только по новому указанию преподавателя |
| Требование из ГОСТа | `Г-` | Обязательно, если реализуется соответствующий алгоритм |
| Рабочее предположение | `РП-` | Не подтверждено. Может быть отменено без последствий для требований |
| Открытый вопрос | `ОВ-` | Ответа нет. Решение не принимается до ответа или явного указания пользователя |

У требований `ТП-` указан источник:

- **[явно]** — указание преподавателя, переданное пользователем;
- **[все]** — совпадает в моих заметках, заметках старосты и на фото доски;
- **[заметки]** — есть в обеих заметках, на фото не различимо или отсутствует;
- **[мои заметки]** — только в моих заметках. Требование принимается,
  но его детали не уточнены.

## 3. Подтверждённые требования преподавателя

### 3.1. Криптография — общее

**ТП-1. Ручная реализация криптографии.** [явно]
Все криптографические алгоритмы в рамках задания реализуются самостоятельно,
без использования готовых реализаций самих алгоритмов. Как минимум это:

- Стрибог-512 по ГОСТ 34.11-2018;
- Кузнечик по ГОСТ 34.12-2018;
- режим работы Кузнечика по ГОСТ 34.13-2018;
- ЭЦП по ГОСТ 34.10-2018;
- RSA-32768.

**ТП-2. Допустимые средства стандартной библиотеки.** [явно]
Обычные возможности стандартной библиотеки языка — целые числа, `bytes`,
файловый ввод-вывод, генерация случайных чисел, работа с сетью и т. п. —
не считаются готовой реализацией криптографии, если преподаватель
отдельно этого не запретил.

**ТП-3. Кузнечик, Стрибог и ЭЦП выполняются по ГОСТам.** [заметки]
«1–4 делаем по ГОСТу» (мои заметки) и «2,3 по ГОСТам, ЭЦП» (староста).
Слова преподавателя: «ЭЦП в проекте тоже гостовская и самостоятельно написанная».

### 3.2. Криптография — алгоритмы

**ТП-4. Хэширование паролей: Стрибог-512 с солью.** [все]
Пароли хранятся в БД в виде хэша Стрибог-512 с солью.

**ТП-5. Симметричное шифрование: Кузнечик.** [все]

**ТП-6. Асимметричное шифрование: RSA с модулем 32768 бит.** [все]
ГОСТа на RSA нет; алгоритм реализуется вручную (ТП-1).

**ТП-7. Электронная цифровая подпись.** [все]
Гостовская, самостоятельно написанная (ТП-1, ТП-3).

### 3.3. Пользователи и доступ

**ТП-8. Три роли:** гость, пользователь, администратор. [все]

**ТП-9. Форма регистрации с проверкой полей регулярными выражениями.** [заметки]
Состав полей и правила проверки не определены (ОВ-7).

**ТП-10. Трёхфакторная аутентификация (3FA).** [все]
В моих заметках записано «NFA / 3FA» (ОВ-19). Состав факторов не определён (ОВ-1).

**ТП-11. Почтовый сервер для 3FA.** [заметки]

**ТП-12. Форма восстановления пароля.** [все]

**ТП-13. Коды восстановления / коды одноразового доступа.** [заметки]
Один это механизм или два — не определено (ОВ-9).

### 3.4. Сообщения

**ТП-14. Пользователь после входа вводит сообщение.** [мои заметки]

**ТП-15. Сообщение шифруется одним из двух способов: RSA или Кузнечик.** [мои заметки]

**ТП-16. Пользователь видит список своих зашифрованных сообщений.** [мои заметки]

**ТП-17. Каждое сообщение можно скачать вместе с ЭЦП в формате PDF.** [мои заметки]
Содержимое PDF не определено (ОВ-4).

## 4. Требования, следующие из ГОСТов

Ниже — только то, что прямо задано стандартами. Всё, что стандарты оставляют
на усмотрение разработчика, вынесено в открытые вопросы.

### 4.1. Общие

**Г-1.** Каждый алгоритм, для которого в ГОСТе есть контрольные примеры,
проверяется автоматизированными тестами по этим примерам, включая
промежуточные значения, если они приведены. Успешного round-trip
(зашифровать → расшифровать, подписать → проверить) недостаточно.

**Г-2.** Текстовый слой PDF-файлов ГОСТов содержит ошибки распознавания
(смешение кириллицы и латиницы, потерянные символы). Константы и контрольные
значения сверяются с изображениями страниц, а не копируются из текстового слоя.

**Г-3.** Порядок записи векторов в ГОСТах: старшие разряды слева, нумерация
справа налево с нуля. Преобразование между строками байтов приложения
и векторами ГОСТа должно быть явно определено и покрыто тестами.

### 4.2. ГОСТ 34.11-2018 — Стрибог

**Г-4.** Функция хэширования с длиной хэш-кода 512 бит, IV = 0⁵¹².

**Г-5.** Если для ЭЦП выбрана кривая с 2²⁵⁴ < q < 2²⁵⁶, дополнительно нужна
функция с длиной хэш-кода 256 бит, IV = (00000001)⁶⁴ (см. Г-15, ОВ-12).

**Г-6.** Контрольные примеры: приложение А, примеры 1 и 2, для 512 и 256 бит.

**Г-7.** Стандарт не определяет способ использования соли (см. ОВ-11).

### 4.3. ГОСТ 34.12-2018 — Кузнечик

**Г-8.** Блочный шифр с длиной блока 128 бит и длиной ключа 256 бит.

**Г-9.** Контрольные примеры: приложение А.2 — преобразования S, R, L,
развёртывание ключа (константы C₁…C₈, ключи K₁…K₁₀), зашифрование
и расшифрование блока с промежуточными значениями.

**Г-10.** Шифр «Магма» (блок 64 бита) из того же стандарта заданием не требуется.

### 4.4. ГОСТ 34.13-2018 — режимы работы

**Г-11.** Используется один или несколько режимов из стандарта:
простой замены (ECB), гаммирования (CTR), гаммирования с обратной связью
по выходу (OFB), простой замены с зацеплением (CBC), гаммирования с обратной
связью по шифртексту (CFB), выработки имитовставки (MAC). Выбор — ОВ-3.

**Г-12.** Требования выбранного режима соблюдаются полностью:

- ECB и CBC требуют дополнения сообщения; однозначное восстановление
  гарантирует только процедура 2 (п. 4.1.3);
- синхропосылка для CBC и CFB — непредсказуемая (случайная или псевдослучайная);
- синхропосылка для CTR — уникальная для каждого сообщения на одном ключе,
  длиной n/2 бит;
- синхропосылка для OFB — непредсказуемая или уникальная;
- ключ режима выработки имитовставки не используется в других режимах
  (примечание к п. 5.6.3).

**Г-13.** Контрольные примеры: приложение А.2 — для каждого режима
с блочным шифром «Кузнечик».

### 4.5. ГОСТ 34.10-2018 — ЭЦП

**Г-14.** Подпись строится на группе точек эллиптической кривой над конечным
простым полем. Алгоритм формирования — п. 6.2, проверки — п. 6.3.

**Г-15.** Длина хэш-кода определяется порядком подгруппы q:
256 бит при 2²⁵⁴ < q < 2²⁵⁶, 512 бит при 2⁵⁰⁸ < q < 2⁵¹².
Подпись — вектор r ‖ s длиной 512 или 1024 бита.

**Г-16.** Ключ подписи d удовлетворяет 0 < d < q; ключ проверки Q = dP.
Для каждой подписи генерируется случайное (псевдослучайное) k, 0 < k < q.

**Г-17.** При проверке подпись отвергается, если не выполнено 0 < r < q и 0 < s < q.

**Г-18.** Параметры кривой удовлетворяют требованиям п. 5.3.

**Г-19.** Стандарт не определяет ни конкретную кривую для эксплуатации,
ни процесс генерации ключей. Параметры приложения А рекомендуется использовать
только для проверки реализации (см. ОВ-12).

**Г-20.** Контрольные примеры: приложение А.2 (256 бит) и А.3 (512 бит).
Они заданы через значения e и k, поэтому реализация должна позволять
подставлять их в тестах.

### 4.6. RSA-32768

ГОСТа нет. Требования стандарта к RSA в проекте отсутствуют;
схема дополнения, экспонента и формат — открытые вопросы (ОВ-13).

## 5. Рабочие предположения

Используются, пока не опровергнуты. Ни одно не закрывает открытый вопрос.

**РП-1.** Предварительные права ролей:

- гость может открыть вход и регистрацию;
- пользователь может работать со своими сообщениями;
- администратор может управлять пользователями.

Подтверждения нет (ОВ-8).

**РП-2.** Неразборчивые части фото доски не считаются требованием.

**РП-3.** Пользователь видит и скачивает только свои сообщения.
