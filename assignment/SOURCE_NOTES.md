# Исходные материалы по заданию

Этот файл содержит сырые заметки с лекции.

Claude не должен считать формулировки ниже идеально точной спецификацией.
Если заметки противоречат друг другу или допускают несколько трактовок,
необходимо зафиксировать неоднозначность.

## Мои заметки

1. RSA - 32768
2. Кузнечик
3. Стрибог - 512
4. ЭЦП
5. NFA / 3FA
6. Форма регистрации (+ регулярки)
7. Форма восстановления пароля
8. Коды восстановления пароля / коды одноразовые
9. Почтовый сервер для 3FA

Дополнительные заметки:

- 1–4 делаем по ГОСТу
- Стрибог нужен для хэширования паролей в БД с солью
- роли: гость, пользователь, админ
- пользователь входит в систему и вводит сообщение
- сообщение можно зашифровать двумя способами:
    - RSA
    - Кузнечик
- пользователь может посмотреть список зашифрованных сообщений
- каждое сообщение можно скачать вместе с электронной подписью в PDF

## ТЗ однокурсника

Документ «ТЗ по лабораторным: информационная безопасность», 2026-11-02, автор — однокурсник.
По словам автора, собран с доски, заметок и сообщения преподавателя.
Сам автор отделяет сказанное преподавателем от своих советов («например», «лучше»,
«не слова препода»). Ниже — краткое изложение по страницам документа.

- **Общее (с. 1).** 9 лаб — один веб-проект: лабы 1–4 — криптография, 5–9 — система входа.
  Готовые криптобиблиотеки не используются; веб-framework, БД и генератор PDF к криптографии
  не относятся. Пример проекта — «защищённый блокнот». Лабы 1–3 нужно уметь показать
  по отдельности, затем они встраиваются в общую систему.
- **RSA-32768 (с. 2–3).** Свои генерация ключей (p, q по 16384 бита, Миллер — Рабин),
  e = 65537, d через расширенный алгоритм Евклида, своё возведение в степень по модулю.
  Длинные сообщения — блоки меньше модуля и случайное дополнение («например, PKCS#1 v1.5»).
- **Кузнечик (с. 3).** Режим по ГОСТ 34.13 («лучше CTR»).
- **Стрибог (с. 3).** Пароли — хэш со случайной солью; «хорошо — PBKDF2/HMAC на Стрибоге,
  минимум — Стрибог(соль + пароль)». Тот же хэш — внутри ЭЦП.
- **ЭЦП (с. 3–4).** Своя, по ГОСТу. Рабочие параметры — из RFC 7836 («например, 512-битная
  paramSetA»). «Выдача ЭЦП»: у каждого пользователя своя пара ключей.
- **3FA (с. 4).** Три шага по порядку: пароль, код на почту, третий фактор — на доске
  не назван (варианты: TOTP, подпись случайной строки ГОСТ-ключом).
- **Регистрация (с. 4).** Логин, email, пароль, повтор пароля; регулярки на клиенте и сервере.
  При регистрации: соль и хэш, ключи ЭЦП, роль «пользователь», коды восстановления.
- **Восстановление (с. 4).** Email → код или ссылка с ограниченным сроком → новый пароль.
  Код одноразовый, в БД — только хэш. Запасной путь — код восстановления.
- **Коды (с. 5).** «Судя по записям» — два механизма: одноразовый код письмом (5–15 мин)
  и 10 кодов восстановления при регистрации. Коды одноразовые, в БД — хэши, генерация —
  криптостойким генератором.
- **Почта (с. 5).** Свой SMTP-сервер на localhost (Mailpit, MailHog или Postfix);
  Gmail и Яндекс не подходят.
- **Роли (с. 5–6).** Три роли, сервер проверяет роль на каждой странице. Таблица прав —
  «разумный вариант, не слова препода».
- **Открыто и в ТЗ (с. 7).** Третий фактор, формат подписи в PDF, допустимость
  некриптографических библиотек.
